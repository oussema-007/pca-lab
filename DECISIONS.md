- 2026-11-07 - Rate limit: **200 requests / 10 s per source IP** (`RATE_LIMIT` in lb01/deploy.sh). Exemption = secret header `LOADTEST_HEADER_NAME` checked with an exact string match, **removed before forwarding** to Odoo. Exempted requests are not tracked at all.

- 2026-11-07 - Logging: `log stdout` + RHEL's `-Ws` unit = straight into journald (`journalctl -u haproxy -f`), works with chroot, no rsyslog change. ## Phase 5
- 2026-11-07 - k6 **v2.3.0** installed from the official GitHub release (sha256 verified) to `/usr/local/bin/k6`; not in Kali's apt.
- 2026-11-07 - k6 resets each VU's cookie jar at the end of every iteration by default: the first request of each iteration then had no `session_id`/`SRV` -> "Odoo Session Expired" on 2/3 of the RPCs. `noCookiesReset: true` = a VU behaves like a browser that stays logged in. RPC success is checked in the JSON body (`result` present, no `error`), not only the HTTP status, because Odoo returns errors with HTTP 200.
- 2026-11-07 - The user probe (`scenarios/probe.py`, stdlib only) uses a persistent HTTP/1.1 connection like a browser and never retries by itself, so every error it logs is user-visible. HAProxy adds `X-PCA-Server` (which node answered) **only** for requests carrying the secret test header, so normal users never see internal names.
- 2026-11-07 - Failover tuning after measuring S1: `option redispatch 1` (redispatch at every retry instead of only the last one, removes ~1 s turn-around pauses on the dead server), `retry-on conn-failure empty-response` (replay when the server died before sending a byte) and `option http-buffer-request` (a request must be fully buffered to be replayable; also blocks slow-POST). Result: crash (SIGKILL) = 0 user-visible errors. Graceful `docker stop` still shows 1 failed probe request out of ~475 at the instant Odoo closes its listening socket (HAProxy 2.4.22 logged `SH`, retried 3 other requests but not this one). Accepted (≤ 1 % criterion), documented; planned work uses drain (S2) which gives 0.
- 2026-11-07 - Replaying a POST is a conscious trade-off: Odoo commits at the very end of a request, so the window where a write is committed but its reply is lost is tiny; listed as a residual risk.
- 2026-11-08 - Rate limit lowered from 200 to **100 requests / 10 s per IP** after measuring: a single client cannot exceed ~11 login pages/s against this backend (2 vCPU), so 200 was never reached (first S4 run: 600 x 200). A real Chromium session (login form + cold web client + Sales list, k6 browser module) = **33 requests**, so 100/10 s keeps a 3x margin for humans.
- 2026-11-08 - S3 measured two ways: (a) as built (3 containers share app01's 2 vCPU) and (b) `CPU_PER_NODE=0.66` (docker update, reverted after) to emulate 3 independent small nodes. Metric = **successful** req/s, because a collapsing node returns fast 503s that inflate raw req/s.
- 2026-11-08 - The hypervisor host was suspended ~2 h 45 during an S3 run (wall clock jumped; Odoo killed its workers for `limit_time_real`). Those runs are kept in results.tsv marked INVALID and were re-run. After the resume, the host is ~2x slower (smoke profile p95 62 ms -> 115 ms); comparisons are always made inside one run.
- 2026-11-08 - DEFENSE-NOTES.md and DEMO-CHECKLIST.md are written in French (the defense is oral, in French); the other deliverables are in English like the brief.
- 2026-11-08 - S1 detection is now measured from the container's real exit (`State.FinishedAt`, NTP-synced clocks) to the DOWN state seen on the runtime API. Measuring from the `docker stop` command included Odoo's graceful shutdown (3–7 s during which the node still serves) and made one run "fail" at 10.2 s although the LB reacted in ~3 s.
- 2026-11-08 - Cold-node flapping observed: after a restart the first requests took 12–15 s (workers warming up on the slowed host), both workers busy -> health check timeout -> odoo1 DOWN again. Fixes: `slowstart 15s` on be_odoo servers and a warm-up (`warm_node` in lib.sh: direct requests from lb01 to the node) in `reset_lab.sh` and before `state ready` in S2.
